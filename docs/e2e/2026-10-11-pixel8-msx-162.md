# Pixel 8: проверка MSX Bridge 1.6.2

Дата: 2026-10-11 (Europe/Moscow).

Последние доработки прошли функциональную проверку на телефоне. Прогон не является полностью чистым: обнаружена воспроизводимая ошибка в core MA — попытка enqueue для плеера без этой возможности. Она не прервала естественные переходы, Repeat и Endless Mix. Core и провайдер во время тестирования не изменялись.

## Проверенный срез

- Pixel 8, Android 17, Media Station X 0.1.165; USB ADB.
- Релиз провайдера `v1.6.2`, commit `44600db39cbb063fddf75ab0f0cacb9391edbbcc`.
- Код MA: head [PR #5868](https://github.com/music-assistant/server/pull/5868), `ad6649e3a1172c23b82b6930845cf051912d76b4`. Head повторно проверен после тестов.
- Код провайдера смонтирован из изолированного release checkout; SHA-256 Python-файлов внутри работающего контейнера совпадают с релизом.
- Python 3.14; models 1.1.221, frontend 2.17.336, hass-client 1.4.0, segno 1.6.6. Проверка прямых версионированных зависимостей MA не выявила расхождений.
- Стенд: `ma-msx-e2e`, 192.168.10.229, отдельный профиль `.cache/ma-msx-e2e-data`. Пользовательский `.ma-data` не изменялся.
- Физическая слышимость тонов подтверждена пользователем; кроме этого, контролировалась активность аудиодекодера MSX в Android.

## Обнаруженный дефект core

`UnsupportedFeaturedException: Player ... does not support enqueueing`.

В первой полной Repeat-матрице зарегистрированы 26 traceback. Runtime плеера объявляет `play_media`, `pause`, `volume_set`, `seek`; ENQUEUE отсутствует. В `music_assistant/controllers/player_queues/stream_feeder.py` постановка следующего элемента вызывает `players.enqueue_next_media` без проверки `player.supports_enqueue`. PlayerController закономерно отклоняет вызов. В Endless Mix также наблюдался один такой traceback.

Это подтверждённая ошибка обработки capability в core; её следует исправлять отдельным PR с проверкой capability перед постановкой и непосредственно перед передачей следующего элемента. Присваивать MSX искусственную capability ENQUEUE ради подавления ошибки не следует. В данном прогоне исправление core не выполнялось. Звуковые переходы на телефоне продолжались; отсутствие влияния на все остальные провайдеры этим тестом не устанавливается.

## Измерения и ограничения

- Forward: ожидаемый source offset 59.09 s, фактический 59 s.
- Rewind: ожидаемый 54.97 s, фактический 55 s.
- Pause: позиция 58.54 s сохранилась; MSX показывал `0:58 / 3:00`.
- Samsung Tizen и Xbox не подключались в этом прогоне; прежняя платформенная проверка не подменяет новые физические тесты.
- Отдельный сценарий радио, непрерывный 30-минутный soak, перемотка во время паузы и акустическая точность seek-маркеров не проверялись.
- Начальные попытки расширенного runner остановились на подготовке/автоматизации: загрузке модели, наложении пересоздания контейнера, обязательном аргументе текущего API и отложенной перезагрузке провайдера. Эти результаты не засчитывались как дефекты воспроизведения.
- В финальном runner после сохранения настроек проверялся новый экземпляр провайдера и устойчивый единственный WS. После native действий проверялись реальные generation/state; UI clock читался из одного свежего accessibility dump. Ошибочные timing/скрытые-controls assertions предыдущих попыток заменены повторным наблюдаемым прогоном, без изменения продукта.

## После тестов

Нормальный запуск контейнера восстановлен; диагностический Unix socket и launcher удалены; HTTP health — ok. Настройки валидных прогонов восстановлены, тестовые очереди остановлены; timeout экрана телефона возвращён к исходным 30000 ms. Стенд оставлен на проверенном срезе 1.6.2. Локальная модель аудиоанализа смонтирована read-only, чтобы последующие старты не зависели от её скачивания.

[Безопасная сводка измерений](evidence/pixel8-msx-162.json). Raw runtime logs и диагностические screenshots остаются в игнорируемом `.cache/msx-162-device`; в публичной сводке отсутствуют URL потоков, credentials, Party tokens и playback nonces.
